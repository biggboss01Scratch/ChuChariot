## 1. 项目目标

构建一个“基于知识图谱的楚国战车三维数字复原与交互展示平台”，形态类似数字博物馆网站。

暂定四个功能模块：

1. 三维模型展示：观察战车整体与部件，支持视角控制、选择和讲解。
2. 结构拆解展示：通过交互式爆炸展示呈现组成层次与连接关系。
3. 知识图谱交互：浏览部件属性、功能和关系，支持点击查询，与三维场景双向联动。
4. 三维动画演示：逐步实现战车装配、马具连接和行驶演示。

最终提交可运行的 Web 系统、项目报告和答辩材料。本次先实现可验证的基础版本，不要求一轮完成全部复原和动画。

## 3. 技术原则与默认方案

优先采用常见、稳定、容易调试的技术。主要探索集中在知识建模、AI 辅助抽取、证据追踪和知识与模型联动。

- Python 作为主后端和离线知识处理语言。
- 若无现成后端，可采用 FastAPI + Pydantic，提供简单 REST/JSON 接口；不引入微服务架构。
- 前端优先复用已有 HTML/JavaScript 及三维实现。没有框架必要性时，使用普通 JavaScript 模块即可；已有团队明确选择时沿用 Vue 或 React，不同时引入多个框架。
- 三维实现先检查已有代码；若需补建，采用 Three.js 等常见 Web 三维方案。模型节点、材质和动画能力须实际检查。
- 图谱正式持久化优先采用单个 Neo4j 实例；首轮可以使用统一 JSON 数据集和 Python 内存图跑通，接口通过小型存储适配层保持一致。若采用临时存储，必须在 README 明确标记，不能宣称已接入图数据库。
- 图片、PDF、GLB 等用普通文件目录存储，数据库只保存资源元数据与地址。
- 空间与装配参数先采用规范化 JSON 配置，不单独部署空间数据库。
- 不默认增加 Redis、消息队列、对象存储服务、向量数据库、登录系统或 LangChain 等编排框架。
- 外部 AI 调用通过一个小模块封装；无密钥时基础平台正常运行，提供人工整理/导入路径，不伪造 AI 调用结果。
- 安装依赖时选择相互兼容的稳定版本并记录；不在本文固定未经环境验证的版本号。

以上是默认实施建议。已有代码或环境不适用时，Agent 应记录理由并采用更简单的可运行替代，不为小型技术选择反复阻塞。

## 4. 底层数据组织

逻辑上分三部分，物理上不必部署三套数据库：

| 部分 | 保存内容 |
|---|---|
| 语义知识图谱 | 类别、部件实例、名称、注音、介绍、功能、组成、连接、尺寸记录和来源 |
| 空间与装配数据 | 坐标系、单位、位姿、连接点、复原状态、步骤及前置依赖 |
| 多模态资源 | 原始报告、图片、音频、模型、动画，以及文件地址和资源元数据 |

通过稳定实体 ID、资源 ID、模型版本和节点标识关联。规范名称可修改，ID 不随名称改变。

必须区分：

1. 类别与实例，如“车轮”和“战车01的左车轮”。
2. 历史实物与数字复原模型，一个实物可对应多个模型版本。
3. 文献记载的尺寸与模型采用的尺寸。
4. 部件组成层次、三维场景父子层次与装配步骤依赖。
5. 原始事实、结构推导和复原假设。

## 5. 本体与数据模型初稿

先用明确的数据模型和关系定义实现轻量本体，无须首轮完成完整 OWL 推理系统。

### 5.1 对象类型

- ComponentType：部件类别，包含规范名、别名、可选注音、通用介绍和父类别。
- Chariot：具体战车或研究对象。
- Component：具体部件，关联类别和所属战车。
- Measurement：尺寸记录，包含类型、数值/范围、单位、近似标记、来源与判断性质。
- Connection：连接记录，关联参与部件，可记录方式、位置、锚点引用和说明。
- SourceDocument / Evidence：文献与证据片段，包含文献 ID、PDF 页码、可选印刷页码、图号、原文或图像定位。
- Resource / ModelVersion：资源、模型版本和文件地址。
- ModelMapping：实体与模型版本、节点标识之间的映射，允许一对多。
- Pose：组件在指定坐标系、模型版本及状态下的位置与朝向。
- AssemblyStep：装配步骤、涉及部件、动作说明、前置步骤、依据性质和动画引用。

属性未知时允许缺失，不用零或虚构数值填充。尺寸保持数值与单位分离，保留原始表达。注音、功能介绍同样需要核查。

### 5.2 核心关系

`SUBCLASS_OF`、`INSTANCE_OF`、`HAS_PART`、`HAS_MEASUREMENT`、`PARTICIPATES_IN_CONNECTION`、`SUPPORTED_BY`、`REPRESENTED_BY`、`HAS_POSE`、`INVOLVES_COMPONENT`、`DEPENDS_ON`。

为每种关系记录中文含义、方向及允许的两端类型。`HAS_PART`默认表示直接组成，间接组成通过路径查询；不能由“列出几个部件”推出“部件清单已经完整”。

### 5.3 事实级证据

给需要追溯的事实建立稳定 fact_id，关联证据，而不仅给整个部件挂一份参考文献。可采用断言节点或关系属性加证据索引，选择一种简单方案统一使用。

至少记录：subject、predicate、object/value、evidence_ids、origin、review_status。

- origin：documented（资料明确记载）、inferred（结构推导）、hypothesis（复原假设）。
- review_status：pending、confirmed、disputed。
- 记录抽取方式及可选模型/提示词版本，便于重现。
- 不把模型自行输出的置信度当作真实概率。
- 不因库中缺少一条关系，就断定该关系不存在。

## 6. 知识构建流程

1. 登记资料和资源，分配 ID。
2. 解析正文、表格与图注；扫描图像必要时 OCR。仅提取 PDF 文本不代表已读取图中全部知识。
3. 按本体输出结构化候选知识，附原文依据及页码。
4. 可选进行一次 gleaning 查漏补抽，合并去重；它不能替代真实性核验。
5. 规范名称、别名、单位与实例归属，保留不同来源的冲突说法。
6. 人工审核，或先进入待审核区；未经确认的知识不得默认显示为已证实事实。
7. 执行格式、引用和关系检查，导入正式知识数据。
8. 建立实体与模型节点映射，核对复原模型采用的参数。

离线处理脚本与网站运行分开；网站启动和普通查询不得依赖即时重新抽取。导入支持重复执行，避免重复节点或关系。

### 6.1 Model Gleaning：查漏补抽

Gleaning 位于知识与模型构建层，是首轮知识抽取之后、融合核验之前的可选步骤，不是每次用户问答的步骤，也不是模型训练或事实验证。

实施要求：

1. 输入同一资料片段、来源定位、本体版本和首轮抽取结果，请模型仅补充有原文支持的遗漏实体、属性和关系。
2. 每条补充记录携带 evidence_id 或原文引用与页码；缺少证据的输出不得自动进入正式知识库。
3. 与首轮结果合并、规范化并去重；无法判断的实体对应和冲突进入待审核区，不静默覆盖已有知识。
4. 补抽轮数可配置，初步设为最多一轮额外补抽；无新增有效候选时停止，不无限循环。
5. 保留 run_id、资料片段ID、模型标识、提示词/本体版本、轮次、补抽新增与被拒绝记录、调用失败信息，以及可获得的用量和耗时。不记录密钥。
6. 无AI配置时允许跳过并明确标记；提供可导入的人工候选数据格式。失败不得删除首轮结果。

首轮只需建立清楚的处理边界、输入输出格式和运行记录方式；真实模型调用依赖可用配置及资料处理授权，未接通时如实记录。后续以小规模人工核验样本比较开启/关闭补抽时的遗漏、错误与成本，不以新增条数单独证明质量提升。

## 7. 首轮实施范围

目标是实现一个“车轮与车轴相关局部结构”的完整交互样例，同时保留整体模型展示。

### 必须实现

- 原始资源清单及现有代码/GLB能力检查。
- 轻量本体定义、统一数据格式和一组有依据的样例数据。
- Python 后端：实体列表、详情、邻接关系、证据和模型映射查询。
- 页面加载已有模型，支持旋转、缩放、部件选择及高亮。
- 点击模型部件显示知识详情和资料来源。
- 图谱节点与三维部件双向定位；未映射的对象明确提示。
- 局部爆炸展开与复位，保留原始位姿，重复操作不累积漂移。
- 一个简短的分步装配演示，支持播放、暂停或逐步查看；未获核验的顺序标为演示方案。
- README：环境、运行、数据导入、当前完成情况和限制。

若现有 GLB 无法按语义部件选择，先检查是否可依据节点拆分；不得通过简单重命名宣称完成几何分割。允许采用明确标注的简化局部模型验证联动，原模型保持不变。

### 后续迭代

- 扩展到全车部件与更细结构。
- 马具连接、绳索穿引与行驶动画。
- AI抽取批处理和审核界面。
- 图谱数据库完整接入（若首轮使用临时适配）。
- 基于图谱和原文联合检索的问答。
- 参数驱动模型更新或装配候选顺序生成。

不能将这些扩展项默认视为首轮已完成。

## 8. GraphRAG 的预留边界

首轮不把 GraphRAG 作为平台运行前提。保留实体别名、事实证据、原文片段、核验状态和模型映射即可。

后续问答流程：问题解析 → 实体定位 → 图谱与原文检索 → 依据证据生成回答 → 返回证据与相关实体 ID → 前端可高亮部件。

优先实现轻量图谱问答，不因使用LLM抽取就宣称已实现完整Microsoft GraphRAG。装配安全性和几何可行性由专门检查负责，不能交由问答模型保证。

层次划分：Gleaning属于构建层；图谱、空间数据和原文资源属于知识与资源层；GraphRAG联合检索与大模型回答属于知识服务层；问答面板和模型定位属于Web交互层。

问答输出默认不自动写入正式图谱。新线索如需采纳，应进入候选区重新核验。回答应返回证据和实体ID；资料缺失、冲突或推测须明确说明。

## 9. 接口约定草案

- `GET /api/health`：运行状态。
- `GET /api/entities?type=&q=`：实体检索。
- `GET /api/entities/{id}`：属性、介绍、核验标记。
- `GET /api/entities/{id}/relations`：关系与相邻实体。
- `GET /api/entities/{id}/evidence`：证据和来源定位。
- `GET /api/entities/{id}/model-mappings`：模型及节点映射。
- `GET /api/scenes/{id}`：模型资源、坐标与展示配置。
- `GET /api/assembly-plans/{id}`：步骤、依赖、动画引用与依据性质。

可按实际需要合并接口，避免过度拆分。前端不直接持有数据库凭据或AI密钥。浏览器使用相对资源URL，不使用本机绝对路径或file://地址。

## 10. 实施顺序和验收

1. 先调查已有资源，给出简短实现判断，随后执行可逆的首轮构建。
2. 建立数据模型和小样例，优先打通端到端查询与三维联动。
3. 补充爆炸图和局部步骤演示。
4. 用实际结果检查后，再扩展数据量及功能。

首轮验收：

- 按README能在本机运行，无AI密钥仍可使用基础功能。
- 实体ID唯一，关联和资源引用有效；单位合法，尺寸不误归属。
- 类别层次、直接组成和步骤依赖不存在非预期循环。
- 关键知识能追溯到来源；推测与未核验内容可见。
- 模型与图谱双向选择正确，无映射对象有明确反馈。
- 爆炸展开/复位与动画切换不破坏场景状态。
- 对关键数据检查、导入幂等和核心接口编写少量必要测试；进行浏览器实际交互检查。无法检查的部分如实报告。
- 文档同步更新；接手者能够按文档启动、定位模块、执行检查，并区分已实现、已验证、未验证和计划中内容。
- Gleaning边界和记录格式已定义；启用时补充结果可追溯、可去重并可审核，未接通或跳过时明确标记。

## 11. Agent 工作约束

- 保护原始文献、模型、HTML和图片；派生文件放入实现目录。
